# Collaboration Rules

These instructions affect your behavior every session and therefore belong here rather than another document.

* Determine whether a request is exploration, product decision-making, implementation, documentation, or reflection before acting.
* Do not assume the first proposed solution is the settled product decision.
* Ask what problem a request is trying to solve when intent is unclear.
* Preserve settled product decisions unless there is a compelling reason to revisit them.
* Challenge assumptions that weaken clarity, privacy, trust, or the current milestone.
* Do not turn every discussion into an implementation task.

# Product Purpose

Mezzo is a privacy-first voice awareness tool that helps people notice their speaking volume during meetings — gentle visual awareness, not evaluation or interruption.

Mezzo is not a coaching app, dashboard, analytics tool, meeting assistant, or accessibility product. It exists to provide calm, peripheral awareness of speaking volume.

> Always reassuring. Occasionally attention-grabbing. Never distracting.

For the full product definition, values, and "what Mezzo is / is not" boundaries, see `docs/product-experience.md`.

# Non-Negotiable Decisions

These are settled. Do not revisit them without an explicit product-strategy conversation.

* **Mezzo is now Picture-in-Picture–first.** The Mezzo Companion is the sole operational surface. Users still understand only two product concepts — **Mezzo** and **Mezzo Companion** — but Mezzo (the browser page) is no longer where anything happens beyond one narrow, deliberate exception: it introduces the product, requests microphone permission, and launches the Companion — nothing else. This supersedes every "both surfaces" framing that predates it — see Product Architecture below for what changed concretely, and the microphone-permission entry below for why the permission gate itself lives here rather than in the Companion.
* There is no universal, fixed baseline. Useful monitoring requires calibration, because microphone gain, distance, environment, and speaking level all differ across users and devices.
* Every new monitoring session requires calibration unless the user explicitly starts with an existing saved profile as-is. Calibration is one of the two ordinary ways a session begins, not a rare first-run step.
* A **saved profile** is a persistent, reusable identity — an id, a name, and a fixed position in the library (e.g. "Kitchen," "Home Office," "Coffee Shop"). A **calibration** is just the current measurement attached to that identity. A **temporary calibration** exists only for the current session unless the user explicitly saves it.
* **Recalibrate**, from the Companion's Ready screen, is the primary, deliberate way to update a saved profile's calibration in place — same id, same name, same library position. It never creates a duplicate ("Kitchen 2"), never requires renaming, and never requires deleting the profile it replaces. A fresh calibration (Welcome's **Create speaking profile**, or Ready's **Create new profile**) starts out unsaved and stays that way unless the user explicitly chooses **Save profile**, reachable any time from Ready while it's selected — never forced at Stop: a unique name creates a brand-new saved profile; a name that matches an existing saved profile's name (trimmed, case-insensitive — stored display casing is never changed) instead explicitly updates that profile's calibration in place, behaviorally identical to Recalibrate's own **Update** — an equivalent path reached by typing a matching name, not a second, looser way to overwrite something by accident. This is never silent: the naming screen shows a warning and swaps its action from **Save** to **Update** before the user commits to it. There is still no path from a fresh calibration to *silently* replacing an existing profile — only to explicitly, visibly doing so, by name. See "Profile Model" in `docs/product-experience.md` for the full save/replace/discard/delete behavior.
* Recalibrating a **saved** profile never risks losing a completed calibration to protect the profile it targets: on completion it always asks — **Update "{name}"** (overwrites the saved profile), **Keep temporarily** (leaves the saved profile untouched, keeps the new calibration as the unsaved profile instead) or **Discard** — before anything changes. A new calibration (including Recalibrate on the unsaved profile) lands on a result screen instead: **Save speaking profile**, **Keep temporarily**, or **Discard**. At most one unsaved profile (UI: "Temporary profile") exists at a time, held in memory only — never written to sessionStorage or localStorage. It does not survive a Companion close, with one exception: after an involuntary close, the running page's **Reopen Companion** restores it from memory (see below). A later, separate Companion open from Home never resumes into it.
* **Only the Mezzo Companion initiates calibration and recalibration, selects profiles, deletes profiles, and enforces the 5-profile limit.** Mezzo (the browser page) has no calibration UI and no profile UI. Its jobs are introducing the product, requesting microphone permission (see below), and launching the Companion. This retires the earlier "both surfaces can calibrate" model — there is exactly one operational surface for calibration/profiles/monitoring, not two kept in sync; the permission gate is a separate, narrower exception to that, not a reopening of it.
* **Permission should follow understanding.** A first-time user must never click into a raw browser microphone-permission prompt with no context — and separately, microphone permission cannot be reliably requested from inside the Mezzo Companion's own Document Picture-in-Picture window (a real, observed browser constraint, not just a trust preference). Together these are why Home (the browser page), not the Companion, now owns the microphone-permission gate: it explains why access is needed, what's processed locally, and what's never recorded/transcribed/stored, before ever requesting it. This is the one narrow, deliberate exception to "the Companion is the sole operational surface" — calibration, profile selection/management, Ready state, and monitoring remain entirely Companion-only, unaffected.
* **Home reflects the browser's CURRENT microphone-permission state, never first-time-vs-returning visit history.** No persisted onboarding/completion flag exists anywhere in this flow, deliberately. Three mutually exclusive sub-states inside Home: not-yet-granted (explains access, one action, **Enable microphone**, the only click that can ever trigger the browser's real permission prompt), granted (a brief confirmation with its own separate **Open Mezzo Companion** action), and denied (recovery, explains how to fix it; the Companion never opens from here). Granting access and opening the Companion are always two separate, deliberate user actions — never chained into one click — specifically so opening the Companion (`documentPictureInPicture.requestWindow()`) always gets its own fresh user gesture rather than depending on one surviving the real permission dialog's own, unpredictable, human-paced delay. `navigator.permissions.query()` is used narrowly, only to decide which of the three sub-states to show first — it is never authoritative on its own: a `'granted'` result still runs the real acquire/release probe in the background before landing on the confirmed state, so the actual browser-level grant, not the query result, is what ultimately decides the outcome.
* **The Companion's own Microphone Access Blocked screen (C0) is kept, not retired — but its role narrows.** Home's own gate now handles the primary, before-the-Companion-opens denial. C0 remains specifically as the defensive fallback for microphone access being revoked *after* the Companion has already opened (most plausibly during a later Recalibrate) — a scenario Home's gate can't reach since it only runs once, before launch. There are deliberately two recovery experiences now, not one — a genuinely different scenario each, not a duplicate to keep manually in sync.
* The Companion handles live monitoring, Stop, its own Welcome, calibration prep/listening and Ready states, calibration, recalibration, saving, replacing, discarding, deletion, the 5-profile limit, and every Start monitoring — first session and every one after.
* **Every Companion open goes through Welcome or Ready — never straight to Monitoring** — except **Reopen Companion** after an involuntary close, which resumes monitoring if it was running (see the Reopen entry below). With zero saved profiles and no unsaved profile carried over from earlier in the same Companion-open lifetime: Welcome (a distinct first-time screen, not an instant auto-calibrate redirect). Otherwise — one or more saved profiles, or an unsaved profile still available — Ready. There is no more special-cased "first session skips the checkpoint because Mezzo already chose a profile" path — Mezzo never chooses a profile now, so the Companion always needs its own checkpoint.
* **The Ready screen's layout order is fixed**: heading, "Speaking profile" label, a collapsed selector trigger, contextual actions for whichever profile is selected, Start monitoring, privacy disclaimer — always in that order. Selecting a different profile updates the selector's contents and the contextual actions beneath it; it never restructures the screen around them. The contextual line is **Save profile** for the unsaved profile, or the "Made before the new sound filter. Recalibrate" note (its **Recalibrate** an inline link) for a saved profile without `peakDb`; **Recalibrate** (a per-row icon) and **Create new profile** (the panel footer, which shows the five-profile-limit screen at the cap) live inside the selector panel. Every calibration (Welcome's **Create speaking profile**, **Create new profile**, **Recalibrate**) is two steps, each a prep screen then a listening screen (2026-10-26, "say it once, then count"; the C1 intro screen and the "Get ready" 3-2-1 are retired): Step 1 prep → 3s room listening → Step 2 prep → 6s voice listening → result. Prep screens wait for **I'm ready** and measure nothing. Recalibrating a saved profile puts one "Recalibrating {name}" header bar (the Decision bar) on all six screens of the flow, result included (`applyRecalibrationBar()`); the temporary profile's recalibration, first-time setup and Create new profile have none. Cancel returns to where calibration started (Welcome or Ready, `calibrationIntent.source`); Try again after a voice failure returns to Step 2 prep, keeping the room reading (`retryVoice()`). Full behavior: `docs/product-experience.md`'s "Calibration".
* **The Ready heading** — "Ready for your first conversation" only right after first setup: monitoring has never started (a one-way, persisted flag, `getHasStartedMonitoring()`) and no saved profile exists. Otherwise "Ready when you are" (`readyHeadingCopy()`, `src/mezzo-session.js`). "Ready for your next conversation" is retired (2026-10-23).
* **Every profile save/replace/delete decision is a genuinely separate, full-screen state** — never a modal, never an in-dropdown confirmation, never a browser-native `confirm()`. This covers: the new-profile result screen, confirming a saved-profile recalibration's Replace/Keep temporarily/Discard outcome, naming a new saved profile (and the existing-name warning that swaps its action to Replace), the five-profile-limit notice, and saved-profile delete confirmation.
* Closing the Companion always stops monitoring and releases the microphone. **Close Companion** (on the running page) then returns Mezzo to Home. **Any other close** — another picture-in-picture window replacing it (Chrome allows one at a time, newest wins, so Meet's mini window closes the Companion) or its own native ✕, which Mezzo cannot tell apart — keeps the page on the cream running surface with **Reopen Companion** and **Done**. Reopen opens it again from that click with the same profile (a temporary one included) and resumes monitoring if it was running; Done returns to Home. Implemented as `reopenOffer`/`reopenCompanion()`/`dismissReopenOffer()` in `src/mezzo-session.js`; `endSession()` sets `closingOnPurpose` so Close Companion never produces an offer.
* **Open Mezzo Companion**, from Home — reachable only once Home's own microphone-permission gate has confirmed access (see above) — and **Reopen Companion** are the only actions that open the Companion. Open Mezzo Companion does not itself choose a profile or start monitoring — the Companion decides Welcome vs. Ready and takes it from there.
* `index.html`/`landing.js` (via the shared `src/home-dock.js` controller) plus `src/mezzo-session.js` are the single source of truth for the monitoring session. The same page — the public homepage — is Home before a Companion exists, and takes on the Dock role once one does — one file group, not two. `try-it.html` is retired to a static redirect to `index.html`, kept only for old bookmarks, cached service-worker entries, and the browser extension's existing entry URL; it has no script or logic of its own. See Product Architecture.
* Session state, Companion state, monitoring state, and layout mode are four separate concerns and must never be conflated or inferred from one another.
* There is no Close Companion button anywhere in the Companion — the native Picture-in-Picture window-close control is the only way to close it directly.
* The Dock (the cream **running** page) has one dedicated control while the Companion is open: **Close Companion**, a quiet charcoal text link — a recovery action for closing the floating window when its native ✕ isn't reachable (e.g. it's behind other windows). It has the exact same effect as the Companion's own native window-close control: stops monitoring, closes the Companion, and returns Mezzo to Home. This is the one deliberate exception to "the Dock has no operational controls" — it is a lifecycle/recovery action, not a duplicate of anything the Companion itself does, and it isn't framed as a second way to decide the user is done. The Dock must never expose calibration, profile, monitoring, Stop, or Save controls. After an involuntary close it shows Reopen Companion and Done instead (above). The one-time Meet tip that briefly lived here is retired (2026-10-23). A monitoring session otherwise ends by closing the Dock (which closes the Companion too) or by closing the Companion natively.
* **Document Picture-in-Picture support is required to use Mezzo.** Browsers without it show a clear unsupported-browser message, not a parallel in-page calibration/monitoring implementation. This retires the old no-Companion-support fallback (full in-page calibration + monitoring) — maintaining two operational implementations directly contradicts having one operational surface.
* Speaking profiles are local-only: stored in the browser, no account required, never uploaded or synced to any server, as part of the profile experience. This describes profile data specifically — it is not a claim that Mezzo makes zero network requests. Anonymous, audio-free product-usage analytics exist separately (see Privacy Principles) and never carry profile content, audio, or volume data.
* Privacy is primarily demonstrated through architecture. Surface it in user-facing copy where it materially affects trust, but do not repeat privacy messaging indiscriminately across every screen.
* Compact mode is an intentional peripheral-awareness mode, not a responsive fallback for small windows.
* **Monitoring opens in Compact** (220×220), the peripheral default; Expand is an explicit action. Monitoring's presentation keys off the window's **short side** (`data-size-band` on the screen, set by `ringLayout()` in `src/mezzo-session.js` on every resize, never by `layoutMode`): Mini < 160, Compact 160–299, Expanded ≥ 300, edges 8/12/16. The Range Ring is sized for full Outside by its solid band: `edgeForBandExtent()` (`src/range-ring.js`) turns the space between the top row and Stop, less twice the edge spacing, into the edge, so the band never reaches the name or Stop; the glow isn't counted and may reach into the gap and under the name (which gets a feathered background-colored oval behind it, only while the ring is Outside), never the controls, and stays inside the window's width (`ringEdge()`). The Compact band caps the band at 0.1 of the edge (`COMPACT_BAND_CAP`, via `scaledBand()`): a 90px edge at 220×220, band about 3px to 9px. Controls are 32×32 with #B0AB9E icons at full opacity; Stop is icon-only below Expanded and a labeled "Stop" button at Expanded, always named "Stop monitoring"; Mini reveals its controls only on hover/focus. There is no Pause.
* The Companion's sizes: Monitoring Expanded 382×512 (`MEZZO_COMPANION_EXPANDED_SIZE`, `src/mezzo-session.js` — the same size as every pre-monitoring screen since 2026-11-02, so Ready → Expanded never resizes the window; was 382×480, and 290×420 before 2026-08-18) and Compact 220×220 are still fixed as the two explicit `layoutMode` targets `applyLayoutMode()` resizes to on an explicit Expand/Compact action — manual resizing between and around those targets is freeform (no aspect-ratio lock, no `resizeTo()` in response to a resize event) and handled entirely by presentational CSS breakpoints on the Monitoring screen itself, not by changing either constant. Every pre-monitoring screen — Welcome, the calibration prep and listening screens, the processing screen, the microphone-blocked screen, Ready, and every full-screen decision state — shares one fixed content size, **382×512** (`MEZZO_COMPANION_READY_WIDTH`/`MEZZO_COMPANION_READY_BASE_HEIGHT`, `src/mezzo-session.js`), unconditionally: it no longer depends on saved-profile count. **Measured in real Chrome 156 (2026-11-02):** `requestWindow()`'s width/height are the content size (382×512 content, 382×546 outer), and `preferInitialWindowPlacement` keeps a reopen at that size; `resizeTo()` sets the OUTER size, so content sizes go through `resizeCompanionToContent()` (Ready and Expanded both do; Expanded used plain `resizeTo(382, 512)` until then, leaving its content 34px short, so Stop grew the window). Compact's outer `resizeTo(220, 220)` lands at 240×186 content: Chrome won't go narrower than 240. To measure real sizes, run a script with `chromium.launch({ channel: 'chrome', headless: false })` and `newContext({ viewport: null })`; the regular Playwright suite can't. The Ready screen's selector expands into an overlay panel with its own internal scroll (`max-height:260px; overflow-y:auto`), positioned over the card's own bounds, rather than an always-visible list that used to make the window itself grow — see "Companion Sizing" under Engineering Notes for the full history of both the retired dynamic-height model and this fixed one. Ready and Monitoring Expanded share one size (382×512) but stay separate constants: Expanded is `applyLayoutMode()`'s Expand target.
* Every full-width, single-column Companion action button (Start monitoring, and every full-screen decision state's primary/secondary action — Replace, Keep temporarily, Discard, Save/Replace, Delete, Try again) shares one CSS rule capping it at `max-width: 320px` with `margin-inline: auto` — so a manually-widened Companion window never stretches these into oversized buttons. Save profile and the selector panel's actions are links or icons, not full-width buttons, so this cap doesn't apply to them; Compact controls and selector rows are a different pattern too and are never subject to this cap either.
* The Dock (running page) shows a status line, "Monitoring is not active" / "Monitoring is active" (`dockStatusCopy()`, `src/home-dock.js`, collapsed from `SESSION_STATES` to one boolean), "Your Companion is open", "Keep this page open while using Mezzo. Closing it will also close the Mezzo Companion.", and Close Companion. The status line is the only thing that changes; it never reads zone or profile.
* **No site footer, on any page.** Home has none, and Privacy is in the main nav; the shared `.site-footer` styles were removed (2026-10-23). The Privacy page instead has an "On this page" outline generated from its own H2/H3s (`src/page-outline.js`): a sticky left column on wide screens, a collapsible list above the text on narrow ones.
* Home's microphone-permission blocked state has no in-page recovery button (retired 2026-08-17 — see Engineering Notes). Recovery is the browser's own address-bar site controls plus a manual reload; copy is generic ("your browser," never a named browser) since Mezzo supports Chrome and Edge, not Chrome alone.

# Privacy Principles

Privacy is a product principle, not a marketing feature.

Mezzo:

* processes audio locally
* never records audio
* never stores audio
* never transmits audio as part of the core monitoring experience
* never transcribes speech
* never analyzes conversation content
* never identifies speakers

Whenever implementation decisions affect privacy, choose the option that most clearly preserves user trust.

If product messaging cannot honestly describe the implementation, change the implementation before the messaging.

Copy rules (2026-10-25), enforced by `src/copy-style.test.js`:
* **One privacy line** under a primary action, everywhere: "Mezzo only measures volume. Nothing you say is recorded." (The extension popup's "Opens in its own window." / "Only measures volume." is its space-limited variant.)
* **"speaking profile(s)" in sentence case** in source text; uppercase labels get their caps from CSS `text-transform`, never from the string.
* **No em dashes in user-facing copy** (HTML text and attributes, Companion and extension strings): two sentences, a colon or a comma instead. Code comments and developer-only logs/errors are exempt.

Copy that names a profile wraps the name in curly quotation marks (“ ”, 2026-10-23; straight quotes are retired): `Delete “{name}”?`, `Update “{name}”`, `Save it to “{name}”?`, `A profile named “{name}” already exists.`, `Profile “{name}” updated`.

**Save profile** is Ready's own naming-step primary action for a name that doesn't match any existing saved profile — reachable any time an unsaved profile is selected, never forced at Stop. When the typed name matches an existing profile instead, the action becomes **Update** — reflecting that it does the exact same thing a saved-profile Recalibrate's own **Update** does (updates that profile's calibration in place, same id/name/library position), just reached a different way (typing a matching name instead of choosing Recalibrate). Unlike the retired model, none of Update, Keep temporarily or Discard (Recalibrate's outcomes) starts monitoring directly — both simply return to Ready with the appropriate profile selected; there is no more "primary action also starts monitoring" pattern to interpolate a label for.

Terminology rules:

* **Mezzo** is the whole product — never use it to mean only the floating window. It is also, specifically, the name of the introductory page users land on before the Companion opens — that page has no separate public name of its own (see **Home** below).
* **Mezzo Companion** is the user-facing name for the floating always-on-top window. Use it on first mention in user-facing explanatory copy; **Companion** is acceptable afterward. Internal documentation may generally say **Companion** once the term is established.
* **Home** is internal-only shorthand for what Mezzo (the browser page) shows before a Companion exists: an introduction to the product, its microphone-permission gate (**Enable microphone** / **Open Mezzo Companion** / recovery — see the Non-Negotiable Decisions entry above, "Permission should follow understanding"), and, once granted, **Open Mezzo Companion** itself. Not a user-facing name — users still only ever hear "Mezzo" and "Mezzo Companion." Home has no calibration UI and no profile UI.
* **Dock** is internal-only terminology (retired name: **Anchor page**) for what the same browser page becomes once the Companion is open: a minimal status surface with exactly one control, Close Companion — never surfaced in UI copy (see Internal-only terms below).
* **Speaking Profile page** is retired terminology — profile selection, calibration, and recalibration are Companion-only now; there is no separate page-level implementation of any of it. See `docs/ux/speaking-profile-flow.md`'s own retirement note.
* **Monitoring session** (or just **Session**) refers only to a period when monitoring is active — not the Dock, the browser tab lifecycle, the Companion window's lifecycle, or the overall time Mezzo stays open during the day.

Two rules that directly affect what gets built:

* **Open Mezzo Companion**, from Home, is the only action that opens the Companion — and the only thing it does. It never chooses a profile and never starts monitoring by itself. It is also never the same click as **Enable microphone** — granting microphone access and opening the Companion are always two separate, deliberate actions (see the Non-Negotiable Decisions entry above). The Companion, once open, decides Welcome (zero saved profiles, no unsaved profile) vs. Ready (otherwise), and **Start monitoring** — reachable only from the Companion's own Ready screen — is what actually begins a session, first one and every one after alike. There is no "Open Companion"/"Re-open Companion" action distinct from this, and no page-side Start monitoring anymore.
* **Create speaking profile** (Welcome), **Create new profile** (Ready), and **Recalibrate** are Companion-only controls now — there is no second, page-level implementation to keep in sync with. This retains the earlier unification (all replaced the old split "Create New Speaking Profile" (Mezzo) / "Create New Profile…" (Companion) / "Calibrate for this session") while retiring the "both surfaces" framing that unification was originally built for.

Never introduce alternate names for the Companion in code or UI: no Companion Window, Floating Companion, Control Room, Control Page, "Bring Companion to Front," or "Pop Out."

Internal-only terms — never surface to users: Marketing Site, Onboarding, Home, Dock, Document Picture-in-Picture. **Marketing Site**, **Onboarding**, and **Home** now all describe the same single page (`index.html`) at different moments — introducing the product, gating on microphone permission, and handing off directly to the Companion — not three separate implementations to keep in sync; use whichever of the three reads most naturally in context.

Avoid outdated terms that no longer describe the implementation: "Session Window" (retired), "Open Companion" (never existed as a real action), "Everyday Conversation" (retired — see Profiles below; every session now starts from an actual calibration), "Create New Speaking Profile" and "Create New Profile…" (retired — both replaced first by the unified "Calibrate for this session," then by the current "Create speaking profile"/"Create new profile" split, see above), "Calibrate for this session" (retired — see the Ready-screen PRD's implementation for what replaced it: "Create speaking profile" from Welcome, "Create new profile" from a saved-profile Ready state), "Anchor page" (retired — see **Dock** above), "Replace" (retired as a UI string 2026-10-23 — the same action reads **Update**, `Update "{name}"`), "Keep as unsaved" (retired as a UI string — the button reads "Keep temporarily"; # Product Architecture

Two named experiences, from the user's perspective. Full description: `docs/product-experience.md`'s "Product Mental Model."

## Mezzo

Implemented as `index.html`/`landing.js` — the public homepage doubles as Home and the Dock, the same two-state model a separate `try-it.html` page used to own on its own. `landing.js` owns only what's specific to this page's own marketing presentation (scroll-triggered reveals, the initial page fade-in); the actual Home ↔ Dock state machine — session creation, direct Companion launch, Dock status mapping — lives in the shared, reusable `src/home-dock.js`, which also owns `src/mezzo-session.js`'s session logic:

* **Home** (before a Companion exists): the homepage itself — hero, "how it works," philosophy — introduces the product and, as one narrow, deliberate exception, gates on microphone permission before anything else can happen. Its hero reflects the browser's current, live microphone-permission state (never first-time-vs-returning visit history — no persisted flag anywhere) as one of three mutually exclusive sub-states: not-yet-granted (**Enable microphone**, the only click that can ever trigger the browser's real permission prompt), granted (a brief confirmation with its own separate **Open Mezzo Companion** action), or denied (recovery; the Companion never opens). Granting access and opening the Companion are always two separate, deliberate clicks — never chained into one — so `documentPictureInPicture.requestWindow()` always gets its own fresh user gesture rather than depending on one surviving the real permission dialog's own human-paced delay. Still no profile UI, no calibration UI — all of that stays in the Companion. Clicking Open Mezzo Companion opens the Companion directly; it never navigates anywhere first.
* **Dock** (once a Companion exists): the same page, with its marketing content hidden and a minimal status surface shown instead — see Non-Negotiable Decisions for its one control (Close Companion) and what it must never expose.

`src/mezzo-session.js` still owns microphone access, monitoring engine, audio processing, active profile, calibration state, session lifecycle, and the Document Picture-in-Picture integration — Home and the Dock never touch any of that directly. Home's two calls into it (via `src/home-dock.js`) are `requestMicrophoneAccess()` (the permission gate — a plain acquire/release probe against the same shared `AudioProcessor` instance, bypassing `calibrationController` entirely, since it's not a calibration attempt) and `startMonitoring()` (the one that opens the Companion). Neither duplicates microphone ownership — both reuse the exact instance calibration itself uses once the Companion is open.

`try-it.html` is retired to a static redirect to `index.html` (see `monitoring.html` for the same pattern, itself also now redirecting straight to `index.html` rather than chaining through `try-it.html`) — kept only so old bookmarks, cached service-worker entries, and the browser extension's existing entry URL keep working. It has no script, no state, and no logic of its own; `try-it.js`/`try-it.css` no longer exist. There is exactly one Home/Dock implementation now, not a page-level one plus a homepage-level one.

## Mezzo Companion

Implemented via the Document Picture-in-Picture API, built by `src/mezzo-session.js`.

Owns: live visualization, monitoring awareness, peripheral feedback, calibration, recalibration, profile selection, profile deletion, the 5-profile limit, Start monitoring — first session and every one after — Stop, its own window state, and its own layout mode. Never contains an End Session action — that stays Mezzo's responsibility (Home/Dock, via the page closing or Close Companion). Never contains a Close Companion action — the native window-close control is the only way to close it.

**States** — Welcome, the two calibration prep screens, the listening screen (Calibrating), the microphone-blocked recovery screen (C0 — now specifically the fallback for access revoked *after* the Companion has already opened, since Home's own permission gate handles the primary, before-open denial), Ready, every profile save/replace/delete decision state, and Monitoring — must never be built as one screen with elements toggled; each is a distinct experience with a distinct purpose. **Welcome** is a first-time-only screen (zero saved profiles, no unsaved profile), reached only once per Companion-open lifetime, before the first calibration ever begins — not an instant auto-redirect into Calibrating. Full behavior: `docs/product-experience.md`'s "Companion States."

**Sizes**, one per state — see the Non-Negotiable Decisions entry above for exact pixels. Ready's width is fixed but its height is computed from the saved-profile count; Welcome and Calibrating reuse Ready's fixed baseline size; Monitoring is meaningfully different only in its Expanded/Compact **layout mode**. Full behavior: `docs/product-experience.md`'s "Compact Companion."

## Profiles

* A saved profile is a persistent, reusable identity for an environment or situation (e.g. "Kitchen," "Home Office") — not a single-use calibration. Its calibration can be refreshed via Recalibrate without changing its id, name, or library position.
* The Companion runs calibration, runs recalibration, saves a temporary calibration as a new profile, deletes profiles, and enforces the 5-profile limit — all Companion-only now. There is no second, page-level implementation of any of this to keep in sync.
* A temporary, session-only calibration lives only in session state until explicitly saved as a new profile. If never saved, it is discarded when the session ends — it is never silently promoted to a saved profile, and it never overwrites one.
* Renaming a saved profile does not exist as a feature yet. If it's ever built, it belongs in the Companion's Ready screen alongside delete — not deferred to a page-level profile-management surface, since none exists.

### Canonical Runtime Profile Shapes

Exactly two shapes exist now, and only two:

```js
// Saved profile — used AS-IS for a saved-profile monitoring session, never
// wrapped. This is the literal object src/profiles.js's getSavedProfiles()/
// addSavedProfile()/updateSavedProfile() already produce.
{ id, name, speakingDb, spreadDb, calibratedTs, peakDb?, roomNoiseDb? }

// Temporary calibration — the ONLY shape `temporary: true` ever appears on.
{ name: "Current speaking range", speakingDb, spreadDb, calibratedTs, peakDb?, roomNoiseDb?, savedProfileId: null, temporary: true }
```

`peakDb` is the calibration's 95th-percentile level + 1.5 dB, in dB above `speakingDb` (the end of range); `roomNoiseDb` is the room's absolute median level during calibration's Step 1 (the 3s room step; the controller accepts room readings only then, via `recordRoomSample()`). Both are optional: a profile without `peakDb` was saved before the speech-band filter, still works with the older spread-based end of range, and `needsRecalibration()` (`src/profiles.js`) makes Ready suggest recalibrating it.

Saved-versus-temporary is decided by `isTemporaryProfile()` (`profile?.temporary === true`) alone, checked first, always — never inferred from the presence or absence of `id`, from name, or from `calibratedTs` recency.

The older `savedProfileId`-wrapper shape (`{name, speakingDb, savedProfileId}`, no `id`) that try-it.js used to construct for a saved-profile selection is retired — every production caller (`chooseSavedProfile()`, the Calibrated screen's commit handlers, the Companion's Ready-screen row selection) now passes the real saved-profile object straight through. `savedProfileId` only ever appears as part of the temporary shape above; `src/mezzo-session.js`'s `profileMetaText()` treats `id` alone as the "Custom" signal.

# Single Source of Truth

`index.html`/`landing.js` (via `src/home-dock.js`) plus `src/mezzo-session.js` own the monitoring session: microphone access, monitoring engine, active profile, calibration, monitoring lifecycle, session recovery, cleanup.

The Companion presents monitoring information. It never independently owns monitoring state.

Four concerns are related but distinct and must never be conflated or inferred from one another:

* **Session state** — whether a monitoring session exists at all, including whether one is currently being prepared via calibration (and if so, in which mode — a fresh session-only calibration, or a recalibration of a specific saved profile). Owned by `src/home-dock.js`/`src/mezzo-session.js`.
* **Companion state** — whether the Companion window is open or closed.
* **Monitoring state** — whether monitoring is active or inactive.
* **Layout mode** — Expanded or Compact, meaningful only while the Companion is open.

Layout mode must never be inferred from window dimensions. Monitoring state must never be inferred from whether the Companion window merely exists.

The Dock (running page) reads only the coarse `SESSION_STATES` enum, collapsed to one boolean (`MONITORING_ACTIVE` vs. everything else) by `src/home-dock.js`'s `dockStatusCopy()`, and, after `COMPANION_CLOSED`, `session.hasReopenOffer()` — never zone, profile, or the Companion's finer inner state, and must not be wired up to do so.

Calibration and recalibration are Companion-only now — `landing.js`/`src/home-dock.js` (Home/Dock) has no calibration UI and does not touch `calibrationController`/`calibrationLock` at all. The calibration logic itself still lives in one place, a shared calibration controller (capture lifecycle, sample collection, validation, result creation, cancellation, and commit commands) inside `src/mezzo-session.js` — "shared" now describes reuse of the same well-tested module across the Companion's own screens (Welcome/the calibration-introduction interstitial/Ready initiate it, Calibrating/Calibration Failed/the microphone-blocked screen/the Update-or-Keep-temporarily decision state render its state), not sharing across two surfaces.

**Naming a new saved profile is Ready-only now, not a pre-monitoring checkpoint.** The old "Calibrated checkpoint" screen's own naming step, and `src/calibration-controller.js`'s `commitSaveAsNewProfile()` (the commit method it called), are both retired: a session-mode calibration lands directly on Ready with the result selected as an unsaved profile, and naming/saving it happens later, any time, via Ready's own Save profile action. `commitSaveAsNewProfile()` itself was removed outright (2026-08-02) once it had been unreachable from any UI path since `a7b8b80` — see Engineering Notes.

The one real, current create path is Ready's own naming screen, which routes through `src/profiles.js`'s `commitSavePromptName()` → `promoteTemporaryProfile()`. `commitSavePromptName()` can also explicitly *update* an existing profile, when the typed name matches one — see the Non-Negotiable Decisions entry above. `resolveSavePromptAction(name, { savedProfiles, maxProfiles })` is the single helper that decides which of create/update/blocked/invalid applies, given a name; `commitSavePromptName()` re-resolves it fresh and then calls `promoteTemporaryProfile()` (create) or the existing `updateSavedProfile()` (update, the exact same function a saved-profile Recalibrate's own Update commit path calls) — never a duplicate persistence path of its own. `src/mezzo-session.js`'s naming-screen UI (`renderM2State()`) only renders whichever outcome that resolver returns — on every keystroke, and again at submit time — it never matches names or checks the profile limit itself.

## Calibration Controller Instance Rule

Exactly one calibration-controller instance should hold the microphone per browser tab at a time — enforced by convention in how the controller is wired up, not by the controller itself, which has no cross-instance awareness. Home/Dock (`src/home-dock.js`) still never touches `calibrationController` at all — this instance remains the Companion's alone within a tab. Home's own microphone-permission gate (`requestMicrophoneAccess()`) is a different thing: it calls the shared `AudioProcessor` (`audio`) directly, bypassing `calibrationController` entirely, since a permission probe isn't a calibration attempt — see the Non-Negotiable Decisions entry above ("Permission should follow understanding"). This still satisfies the one-instance rule: it's the same `audio` instance calibration itself uses, acquired and released completely before the Companion is even asked to open, never held concurrently with a real calibration attempt.

**Ownership tracking (the old `CALIBRATION_OWNERS.MAIN_PAGE`/`.COMPANION` mechanism) predated this model and has been removed** from `src/calibration-controller.js` — `startSessionCalibration()`/`startRecalibration()` take no owner argument, there is no `getOwner()`, and `src/mezzo-session.js` is the controller's one, ungated `subscribe()` listener. Do not reintroduce an ownership/routing signal here; a single surface driving the controller has no second listener to disambiguate against.

**Cross-tab coordination is still fully relevant** (`src/calibration-lock.js`) — two separate browser TABS, each with its own Companion, is unaffected by any of the above. See "Cross-Tab Calibration Lock," below.

## Cross-Tab Calibration Lock

Two separate browser TABS each running their own Mezzo session — each with its own Companion — is a different boundary than the single-tab Instance Rule above; nothing about sharing one JS realm helps here, since two tabs are two entirely separate realms. `src/calibration-lock.js`'s `createCalibrationLock()` closes this gap: a `localStorage`-based lease (`mezzoCalibrationLock`, holding only `{tabId, acquiredAt}` — never audio data or calibration samples), one instance per tab, created inside `createMezzoSession()` alongside `calibrationController` — both now purely internal to `src/mezzo-session.js`, not exposed on the session's public API, since Home/Dock (`src/home-dock.js`) has no calibration UI left to share them with.

localStorage over `BroadcastChannel`: the actual requirement is a synchronous check at the moment a user clicks Calibrate/Recalibrate ("is anyone else already doing this"), not a live, reactive push feed — localStorage already gives that synchronously, with no channel lifecycle to manage.

- **Checked, not enforced by the controller**: `beginCalibrationFlow()` (Companion-only now) calls `calibrationLock.acquire()` *before* touching `calibrationController` or the microphone at all. A rejection shows the existing Calibration Failed screen with `CROSS_TAB_LOCKED` → "Calibration is already open in another Mezzo tab." — no new screen, no mic interaction, nothing to release.
- **Released centrally, not scattered**: `createMezzoSession()` registers one extra `calibrationController.subscribe()` listener that calls `calibrationLock.release()` whenever status reaches `idle` (every commit, cancel, and close route through `reset()`, which lands there) or `failed` (the mic is already free by then). A tab closing outright already calls `calibrationController.cancel()` from its `pagehide` handler, which drives the same `idle` transition — so pagehide needs no separate release call.
- **Held through the whole decision window, not just the mic-holding window — where one still exists**: recalibrating a saved profile keeps the lease held from `acquire()` through the Update/Keep-temporarily decision state — not just while `runCapture()` holds the mic — since the real risk it guards against is broader than the mic alone (two tabs racing `src/profiles.js`'s read-modify-write storage calls). A session-mode calibration (Create speaking profile/Create new profile) has no equivalent decision screen to protect anymore — it commits straight to an unsaved profile and releases the lease immediately on completion, same as any other `idle` transition.
- **Fails open, always**: no usable `localStorage` (locked-down privacy modes, or a non-browser test environment) degrades to an always-allow no-op rather than throwing — never a new point of failure worse than not having this module at all.
- **Stale-owner recovery**: an unrefreshed lock older than `STALE_AFTER_MS` (15s) is treated as abandoned and can be reclaimed; a live tab heartbeats its own lock every 5s so a legitimately long pause on the Replace/Keep-as-unsaved decision state never expires out from under it.
- **Never blocks ordinary saved-profile monitoring**: the lock is only ever checked in `beginCalibrationFlow()` — selecting a saved profile and starting monitoring (the Companion's own Ready-screen Start monitoring) never touches it, in any tab.

# Product Decision Principles

**Awareness before instruction.** Mezzo describes what's happening — it doesn't judge, correct, or score.

Use: Listening, Within range, Approaching end of range, Outside range (2026-08-18 redesign — sentence case, superseding the earlier Title Case set: Quiet, Within Range, Approaching End of Range, Outside Range; "Quiet" specifically is retired in favor of "Listening," everything else is a casing-only change). Never: Too Loud, Warning, Alert, Incorrect, Fix Your Volume, "Quiet," "Within Range," "Approaching End of Range," "Outside Range," or "Approaching Range" (an even earlier retirement, superseded first by "Approaching End of Range," now by "Approaching end of range"). Full state descriptions: `docs/product-experience.md`'s "Monitoring States."

**Chartreuse.** On the website it is the brand accent: primary buttons, the "soft glow" highlight, the nav underline, the selection color. Inside the product (the Companion and the extension) it is only the Outside range nudge — never buttons or UI chrome. `src/chartreuse-scope.test.js` enforces the product side; the website is deliberately out of its scope.

**Visual system (Lantern).** One dark theme (`--color-bg` #2D2E31), Geist/Geist Mono, 3px corners, tokens in `design-tokens/mezzo-tokens.css` — see `docs/prd/range-ring-and-lantern-refresh.md` §4. Color roles: cream (`--color-text`) headings and Companion primary buttons; sage (`--color-link`) text links and the Approaching edge; chartreuse (`--color-accent`) the website's brand accent, and inside the product only the over-range band (see "Chartreuse" above); `--color-voice` the voice circle. The running page is the website's one cream surface (`[data-surface="cream"]`). Mezzo orange (`--hanko-text`, `--zone-*-color`), Noto Serif JP and Sora are retired. The **Range Ring** (`src/range-ring.js`) replaces the wave visualizer (`wave-visualizer.js`, deleted); it reads the engine's committed zone and never classifies zones itself. Tuned values live in `DEFAULT_RING_SETTINGS`, `DEFAULT_ZONE_SETTINGS` (`src/engine.js`) and `DEFAULT_AUDIO_SETTINGS` (`src/audio.js`); `/playground/` is a frozen public copy of the ring tuner (`design/prototypes/ring-tuner.html`) and is excluded from the service worker.

**Preserve calm.** Never introduce flashing, blinking, urgency without reason, aggressive notification patterns, punitive language, or gamification. Attention increases gradually and continuously, never through abrupt interruption.

**Keep the product peripheral.** The Companion is ambient, not a control panel — don't add controls or exposed settings without strong justification. Prefer progressive disclosure over surfacing every option at once.

# Engineering Rules

* Inspect the existing codebase before making large changes.
* Reuse and extend existing systems before rewriting stable ones; prefer a reusable component over a one-off implementation.
* Preserve established behavior unless intentionally changing the experience.
* Keep product logic, the monitoring engine, UI, visualization, and browser integration separated — business logic independent of rendering; the visualization communicates state, it does not compute it.
* Avoid duplicated business logic and duplicated state — one source of truth per concern, referenced rather than copied.
* Favor explicitness over cleverness. Document architectural decisions.
* If implementation appears to conflict with product intent: stop, and clarify the intended experience before changing architecture.

**Running tests.** `npm test` runs the fast Node unit test suite (`node --test src/*.test.js`) — pure-logic tests, no browser. `npm run test:pip` runs the Chromium Document Picture-in-Picture regression tests (Playwright, `tests/`) — these use fake media (`--use-fake-device-for-media-stream`/`--use-fake-ui-for-media-stream`) and cover the real Companion screens the unit suite can't reach. Run `npm run test:pip` after any change to Companion screen flow (transitions between Welcome/the calibration-introduction interstitial/Calibrating/Ready/any decision state/Monitoring), not just `npm test`.

**Process safety when running tests.** This repository is developed and tested directly on the user's live desktop machine, not an isolated CI environment — real browser windows, other applications, and unrelated user processes are running alongside whatever test command is active. Never use broad process-termination commands (`pkill`, `killall`, name-pattern-based `kill`, or equivalent) to address test contention, flakiness, or a slow run — these can just as easily match and kill the user's actual Chrome/Chromium windows, Adobe or other application processes, or unrelated system processes as they can match a genuinely orphaned test process, and a name/pattern match cannot reliably tell the difference. Never terminate Chrome, Chromium, Adobe, system, or user-application processes. A process may be terminated only when its exact PID is confirmed to belong to a process the current test command itself started — never by inference from its name alone. If ownership can't be established with confidence, stop and ask the user before terminating anything. Prefer Playwright's own normal teardown, the repository's existing test commands, and — only if truly necessary — targeted cleanup scoped to a PID this run is known to own.

* **Mezzo Companion title bar (Document Picture-in-Picture).** `src/mezzo-session.js` sets `pipDocument.title = 'Mezzo Companion'` right after the PiP window opens. Found via the linkedom DOM test suite (originally `src/try-it.dom.test.js`, now `src/index.dom.test.js`), not by inspection — this exact race would not have surfaced from calibration-controller.js's own tests (mocked audio, no real DOM) or from Playwright's fake-media-device runs (acquire always "succeeds" there, so the failure path this race depends on never fires).

The extension opens Mezzo in its own normal Chrome window, 800×720, focused and in front, lined up with the meeting window's right edge and clamped to the screen the click came from (`extension/lib/window-manager.js`, `extension/lib/positioning.js`'s `placeWindow()`; the clicked page sends its `screen.avail*`, so no `system.display` permission; it was a bare 480×640 popup, which had no address bar for fixing a blocked mic); its toolbar popup, badge and in-meeting banner are Lantern-styled (`extension/popup/`, fonts bundled since the manifest CSP disallows Google Fonts; the banner registers Geist on the page as "Mezzo Geist", since @font-face in a shadow root isn't applied). `extension/lib/mezzo-url.js`: the live site always, except an unpacked install, whose popup Settings can point it at a preview. Never a second Mezzo: `extension/lib/mezzo-tabs.js` finds Mezzo's Home in any tab of any window by URL, via the existing `https://mezzo-one.vercel.app/*` host permission (no "tabs" permission), and both the popup and the banner bring it forward. The popup has four states (no tab / TAB OPEN / COMPANION OPEN / MONITORING, `extension/lib/popup-state.js`) from `{ companionOpen, monitoring }`, which the page reports from the same session state as the running page's status line (`src/home-dock.js`'s `extensionStatus()`/`createExtensionReporter()`, a same-window `postMessage`) through a content script on the Mezzo site (`extension/content-scripts/mezzo-page-bridge.js`); the popup asks on open (300ms, else TAB OPEN) and updates live. Only those two booleans cross. The popup never opens or focuses the Companion. Tests: `src/extension-popup.test.js`, `src/extension-launch.test.js`; `tests/main-page-states.spec.js` covers the running page, Reopen/Done and the status line.

# Decision Hierarchy

When tradeoffs are necessary, prioritize:

1. User experience
2. Product philosophy
3. Privacy
4. Accessibility
5. Reliability
6. Simplicity
7. Technical elegance

A technically clever implementation that weakens the intended experience is not the correct solution.

When uncertain: does this make Mezzo feel calmer, clearer, and more trustworthy?

When a proposed implementation conflicts with a Non-Negotiable Decision, preserve the decision unless the conversation explicitly revisits it.
